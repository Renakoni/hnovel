## 本轮直接移植的状态语义

| 调用 | 原实现差异 | 参考语义及修正 |
| --- | --- | --- |
| `java.get("bookName")` / `@get:{bookName}` | 只查普通变量，可能读到同名旧值 | 存在书籍时先返回当前 `book.name`；空书名也是有效结果，不向普通变量回退 |
| `java.get("title")` / `@get:{title}` | 同上，且 JS 中修改元数据后读取不一致 | 存在章节时先读当前 `chapter.title`；JS 执行中读活动对象，纯选择规则读同一状态的快照 |
| `java.put` / `@put` | 单独维护临时值，优先于实体变量；实体 API 无法替换它 | 写当前章节，否则写当前书籍；与实体 API 共用变量，后写入的值立即可见 |
| 空变量与大变量 | 清空临时值会重新读出实体中的旧值 | 覆盖当前实体值，空值继续向书籍/来源回退；按参考的 10,000 字符阈值写大小变量存储 |
| 来源回退 | `java.get` / `@get` 未读取 `source.get` 的持久值 | 章节、书籍、传入变量均无非空值后，通过已绑定的 broker 读取来源存储 |
| 无书籍/章节时保存 | 临时值不能由后续来源调用读取 | 经 broker 写 `source.put`；无宿主的纯解释器仍只保存本地测试状态 |
| 搜索第一字段 | 尚未有书名或 URL 时无法辨认当前空书籍 | 像 `BookList` 一样，先创建空书籍状态再解释第一字段，避免将行变量写到来源级 |

## 为什么保留宿主适配，而不是另写解释语义

参考直接持有 Android 的书籍、章节、来源对象和数据库，JS 与选择器都操作它们。
我们的规则运行在隔离进程中，主进程持有来源授权、账号与存储。正确的移植方式是：

1. 在 worker 内复用相同的选择、变量查找顺序和实体行为。
2. 用快照和明确的写入结果跨进程传递实体状态；规则成功后由宿主提交。
3. 来源存储调用经过现有 broker，沿用账号归属、撤销和配额。

这一实现减少了临时变量与实体变量两套状态之间的分歧，同时保留现有进程隔离。
并不声称所有方面优于参考：参考的直接对象模型更简单；我们需要额外验证序列化、
活动对象与快照转换以及调用结束后的状态清理。缺失 API 应按源码实现真实行为，
不能以空函数代替，也不能将网站错误页面当成正文。

参考 App 的真实正文上下文依次执行书名读取/修改、章节变量写入、实体覆盖、空值回退、
特殊键覆盖、大变量和来源回退，得到：

```json

```

`MetadataWireTest` 用相同表达式检查生产 worker 序列化入口，另验纯 `@get` 和连续规则
阶段。`RuleSourceTest` 检查列表初始化的来源值、搜索行变量、详情页之间的实际存取。
底层测试覆盖无脚本时的 `@put`、空元数据、大变量阈值及空值回退。

阅读 3.26.15 APK 未暴露 `chapter.setTitle()`；源码中的 `BookChapter.title` 可变，
产品保留已有 setter 行为。实机同输入用例只使用两端共同可调用的 API，不能把源码与
经过构建处理的 APK 暴露面视为完全相同。
